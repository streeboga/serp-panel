## Каталог проверок и цена переноса

Легенда: 🟢 чистый PHP над HTML, нулевые внешние зависимости · 🟡 внешний API (ключ/квота) ·
🔴 нужен headless-браузер · 🟣 платный LLM-вызов · ⛔ не переносим

### A. Технические / сетевые — 🟢

Код ответа, цепочка редиректов, http→https, слэш в конце, `index.php`/`index.html`,
корректность 404, время ответа, размер HTML, SSL (издатель, срок), favicon (URL, код, тип,
размеры), `robots.txt` (наличие, разбор, устаревшие директивы вроде `Host:`, директива
`Sitemap`), `sitemap.xml` (рекурсивно по вложенным, счётчик URL, дубли, битые), заголовки
безопасности и brotli (K1 из `verify-eq2145.sh`).

Всё это — `Http::get()` + разбор строк. Guzzle и `ext-openssl` уже стоят.

### B. HTML и мета — 🟢

`title` (наличие, длина, дубли по сайту), `description` (наличие, длина, запрещённые символы),
`h1` (количество, совпадение с title), `h2`–`h6` (количество, перескоки уровней), `canonical`,
`meta robots`, `lang` vs фактический язык контента, кодировка, `viewport`, OpenGraph (полный
набор тегов + проверка картинки), Schema.org (JSON-LD: типы, количество, формат), `iframe`,
Flash, устаревшие теги, базовая структура `html/head/body`, `<style>` в теле и `<div>` в голове
(K7 из приёмки).

`DOMDocument` + `DOMXPath` из stdlib. `symfony/css-selector` уже в vendor — если захочется
CSS-селекторов, докидывается только `symfony/dom-crawler` (один пакет).

### C. Контент — 🟢

Размер текста (символы, слова, уникальные), соотношение текст/HTML, процент стоп-слов («вода»),
классическая и академическая тошнота, плотность ключевых слов, распределение ключа по зонам
(title / description / h1 / прочие заголовки / анкоры / остальной текст), облако ключей,
определение языка контента.

Чистая арифметика над текстом. Стоп-слова русского — список в `lang/`.

### D. Ссылки — 🟢

Внутренние и внешние (счётчик, `nofollow`, анкоры), битые ссылки, ссылки на неканонические URL.
Битые требуют HEAD-запроса на каждую — считаем отдельной, более дорогой проверкой.

### E. Изображения — 🟢

Без `alt`, с пустым `alt`, внешние ресурсы, суммарный вес, размеры.

### F. Доступность — 🟢 (разметочная часть)

11 проверок из `tools/a11y/audit.py`: один `<main id="main-content">`, рабочая скип-ссылка,
иконки без имени скрыты, `scope` у `<th>`, `lang`, один `<h1>`, уровни заголовков, дубли `id`,
подписи полей, имена ориентиров, доступные имена ссылок и кнопок. Все — DOM, переносятся дословно.

Контраст и CLS — **не сюда**, см. группу J. В howto прямо описаны грабли: питон не воспроизводит
каскад CSS, первая версия `contrast.py` выдала 67 выдуманных нарушений. То, чего чекер не знает,
обязано уходить в «не проверено», а не в «нарушение».

### G. Юридические — 🟢

Согласие на обработку ПДн у форм, разделы политики, аналитика только после согласия (K2, K3, K10
из приёмки). Для рынка РФ это продаваемая проверка, а стоит она разбора DOM.

### H. Валидация W3C — 🟡

`validator.w3.org/nu` — публичный API, ключ не нужен, но есть лимиты. Раскладывает на ошибки
спецификации / предупреждения / info. Заводится адаптером с собственной квотой на организацию.

**Важно из howto:** не смешивать нарушения спецификации с предпочтениями линтера. На типичной
статье из 182 замечаний `html-validate` 178 были стилевыми, а эталон давал 0 ошибок. Хранить
три корзины раздельно и по умолчанию показывать только первую.

### I. Скорость — 🟡

PageSpeed Insights API: CLS, LCP, FCP, TTFB + полевые данные CrUX. Бесплатно с ключом Google,
лимит по квоте. Ровно то, что в отчёте gvozd показано двумя блоками — лабораторный и полевой.
Кладётся в существующую схему `ConnectedAccount` (ключ на организацию).

### J. Браузерные — 🔴

CLS с виновниками сдвига, контраст по вычисленным стилям реальных узлов, мобильный скриншот,
проверка JS-рендеренного контента, размер шрифта мобильной версии.

Единственная группа, которая **не** переносится «без проблем»: нужен пул headless-Chrome.
Разворачивается как отдельный сервис по образцу скрейперов — адаптер + свой воркер.

### K. LLM-надстройка (arsenkin) — 🟣, кроме интента

Генерация title/description/H1, подбор тематических слов, FAQ, структура страницы — платный
вызов на страницу.

**Интент — исключение, и это наше преимущество.** arsenkin спрашивает у ChatGPT, коммерческий
запрос или информационный. У нас для этого уже есть точные данные: `ClassificationService`
классифицирует домены из выдачи по `SiteType`. Интент выводится из состава ТОП-10 —
если выдачу занимают магазины и агрегаторы, запрос коммерческий. Сигнал объективный,
бесплатный и уже собирается.

### ⛔ Не переносим

- `verify-eq2145.sh` / `verify-eq2146.sh` — приёмка конкретного сайта: nginx, cookie-баннер,
  git, документация. Ценна как **источник формулировок**, не как код.
- `header_drift.py` — специфика eq.team: nginx-сниппет против исходника темы.
- Обёртка над `rechecker.ru` — недокументированные эндпоинты чужого сервиса.
  Перепродавать чужой аудит в коммерческом SaaS нельзя, и сломается оно без предупреждения.
- Проверка на вирусы из отчёта gvozd — отдельный класс задачи, отдельный поставщик.

## Чего нет ни у gvozd, ни у arsenkin, а у нас есть даром

1. **Релевантность против настоящих ключей.** gvozd пишет «релевантность title 66.67%», считая
   от слов самой страницы. У нас `Page` через `Pageable` уже привязана к keyword / cluster /
   category с наследованием `effective_target_url`. Считаем вхождение **целевых** ключей в title,
   description, h1, заголовки, анкоры — по зонам. Это ровно та таблица из отчёта, но осмысленная.
2. **История и диффы.** Разовый PDF не отвечает на «стало лучше или нет». У нас модель
   `SerpSnapshot` уже задаёт паттерн: прогон → снимок → сравнение с предыдущим.
3. **Кросс-страничные проверки.** Дубли title / description / h1 по сайту, страницы в sitemap
   без входящих ссылок, страницы в индексе (`DomainIndexResult`), которых нет в sitemap, и наоборот.
   Постраничный инструмент этого не видит принципиально.
4. **Связка с позициями.** Проседает позиция → показать, что менялось на целевой странице
   между прогонами аудита.

## Механизм

Копия пайплайна индексации домена, который уже работает
(`IndexDomainJob` → `Bus::batch(FetchIndexPageJob)` → `FinalizeIndexBatchJob`). Ничего нового
не изобретаем.

### Таблицы

```sql
site_audits
  id, project_id, domain_id NULL
  scope            -- site | pages | url
  status           -- pending | running | completed | failed | cancelled
  batch_id         -- Bus::batch
  checks jsonb     -- какие группы гоняем; NULL = все дешёвые
  pages_total, pages_done
  score smallint   -- 0..100
  issues_critical, issues_warning, issues_notice
  started_at, finished_at, created_at, updated_at
  INDEX (project_id, created_at DESC)

page_audit_results
  id, site_audit_id, page_id NULL, url, path
  http_status, redirect_chain jsonb, response_time_ms, html_size
  score smallint
  findings jsonb   -- [{check, severity, message, value, expected}]
  metrics  jsonb   -- {title, title_len, h1_count, words, water_pct, ...}
  created_at
  UNIQUE (site_audit_id, url)
  INDEX (page_id, created_at DESC)
```

Две таблицы, находки в JSONB. Никакого движка правил в БД — `ClassificationRule` уже показал,
чего это стоит. Проверки — маленькие классы, список в `config/audit.php`.

### Контракт проверки

```php
interface PageCheck
{
    public function code(): string;               // 'title.length'
    public function group(): CheckGroup;          // technical | meta | content | links | ...
    /** @return Finding[] */
    public function run(PageContext $ctx): array;
}
```

`PageContext` — распарсенный один раз на страницу: ответ (статус, заголовки, тело, тайминги),
`DOMXPath`, извлечённый текст, и `?Page $page` со своими целевыми ключами. Один разбор DOM на все
проверки страницы.

### Джобы (очередь `audit`)

- **`AuditSiteJob`** — оркестратор: собирает список URL, диспатчит батч, вешает `finally`.
- **`AuditPageJob`** — `Batchable`, `RateLimitedWithRedis` по хосту: скачал, прогнал проверки, записал.
- **`FinalizeSiteAuditJob`** — кросс-страничные проверки, счётчики, оценка.

Вежливость: `User-Agent: SerpPanel-Audit/1.0`, лимит запросов на хост, уважение `Disallow`
из robots.txt, потолок страниц на прогон по тарифу (`BillingService`).

### Источники списка URL

1. `sitemap.xml` из `robots.txt` — рекурсивно, покрывает большинство случаев;
2. `DomainIndexResult` — уже собран через `site:`, переиспользуется бесплатно;
3. `Page` проекта — то, что пользователю реально важно;
4. обход по внутренним ссылкам (BFS с глубиной и лимитом) — **фаза 2**, sitemap закрывает 95%.

### API

```
POST   /api/v1/projects/{project}/audits      manager+   {scope, page_ids?, url?, checks?}
GET    /api/v1/projects/{project}/audits                 список прогонов
GET    /api/v1/audits/{audit}                            статус + progress (как index-status)
DELETE /api/v1/audits/{audit}              manager+      отмена батча
GET    /api/v1/audits/{audit}/results                    filter[severity], filter[check], filter[url]
GET    /api/v1/audits/{audit}/diff/{previous}            что изменилось между прогонами
GET    /api/v1/pages/{page}/audit                        последний результат по странице
POST   /api/v1/audit/url                   throttle      синхронно, одна страница, без записи
```

Последний — аналог `scrapers/{scraper}/test`: «проверь вот эту страницу прямо сейчас».
Он же закрывает сценарий `--gate` из howto: внешняя рутина дёргает эндпоинт перед публикацией
и получает пороги (нарушений спецификации 0, критичных 0).

### Фронт

`/projects/$projectId/audit` — запуск, поллинг прогресса и таблица находок. Поллинг уже написан
для `index-status`, берётся оттуда.
